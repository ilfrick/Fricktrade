# Fricktrade v3.0 — Documentazione tecnica dello stato di fatto

**Data audit:** 2026-11-14
**Commit:** `6212507` (branch `v3.0`)
**Metodo:** lettura integrale dei moduli critici, esecuzione di `scripts/alpha_validation.py` sui dati locali,
verifica empirica di funzioni sensibili, git archaeology sui punti controversi.

Questo documento descrive **ciò che il codice fa davvero**, non ciò che la documentazione dichiara.
Le divergenze sono raccolte nella §9 e sono la parte più utile del documento.

## 1. Cos'è

Sistema di trading algoritmico personale, crypto-only, in paper trading. Lo stack è spento dal
2026-08-20 per decisione esplicita (nessuna strategia testata ha un edge out-of-sample positivo).
Il repository resta come infrastruttura di ricerca.

**Stato attuale reale** (verificato su `config/config.yaml`):

| Dimensione | Valore |
|---|---|
| Strategie attive | **1** su 13 istanziabili: `crypto_mean_reversion` (peso 1.0) |
| Venue | Alpaca paper ×2 account (crypto-only) + Binance Spot demo |
| Intervallo dati | 1m |
| Entry | sempre bloccate: `alpha_gate` → `validation_failed` (hold-out −1.08%/trade) |
| Sizing effettivo | ~0.10 × 25% = 2.5% dell'equity per posizione (floor Kelly) |

## 3. Flusso dati e pipeline decisionale

```
Alpaca/Binance REST + WebSocket (+ RSS news, alt-data: Fear&Greed, CoinGlass OI,
     funding, stablecoin flow, order book depth)
        │
        ▼
SymbolManager.resolve_active_symbols()
   prescan Alpaca (~10k → 1.000) → AI filter PPO → return_ranker GBM
   → max_symbols 500 → filtro crypto_only
        │
        ▼
compute_all_indicators()  ~30 indicatori per simbolo, 1 volta/bar
   (atr, atr_pct, bb_upper/mid/lower, rsi, hurst, mfi, vwap_dev, supertrend, ichimoku…)
        │
        ▼
market_state  ←  llm_sentiment (Ollama, 900s TTL), regime HMM, fear&greed, OI
        │
        ▼
CryptoMeanReversionStrategy.generate_signal()
   buy  ⟺  close < BB_lower(50,2σ)  AND  RSI(70) < 30  AND  drop(75 bar) > 1%
        │  confidence = 0.4 + depth × 0.6  (+ booster alt-data / sentiment)
        ▼
_combine_signals()  weighted: Σ(conf × peso) vs min_conviction × SSCM
        │
        ▼
entry_ranking  (%B 40%, MFI 30%, catalyst 15%, funding 15%; penalità 30% se sentiment < −0.4)
        │
        ▼
_check_position_exit()   per i simboli già detenuti  (ordine in §5)
        │
        ▼
_size_order()   equity × max_pos_pct × vol_scale × portfolio_scale × tod_scale × kelly
        │  haircut liquidità, penalità slippage TCA, margine crypto 0.97, floor 8 decimali
        ▼
RiskManager (validate_order, check_crypto_exposure) + alpha_gate
        │
        ▼
OrderQueue (heap FIFO, retry 2×, backoff 10s, timeout 300s) → BrokerRouter
        │
        ├─► Alpaca paper (Realistic, Higher)   ordini market per crypto
        └─► Binance Spot demo                  ordini market per crypto
```

### 3.1 Concorrenza

`_run_symbol_batch()` divide i simboli in **holder** e **non-holder** e usa un
`ThreadPoolExecutor` (4 worker). Gli holder sono processati per primi con una `wait()`
barriera, così le uscite si chiudono prima che partano nuovi ingressi. I non-holder sono
ordinati per `entry_ranking_score` prima del dispatch.

### 3.2 L'imbuto reale delle decisioni

`run_once()` ha **37 motivi di skip** distinti, emessi in `decision_trace`. In ordine di
comparsa nel codice (chi viene prima vince):

```
risk_interpreter_pause → no_active_strategies → strategy_disabled
  → circuit_breaker_backoff → circuit_breaker → sub_min_qty
  → pending_sell_covers_position → close_failed → open_order → no_price
  → min_price → warmup_grace → dust_notional → exit_backoff_active
  → min_hold_active → account_blocked → alpha_gate → stuck_cooldown
  → stuck_blacklist → recent_position → pending_order → pending_leverage_cap
  → limit_block → shorting_disabled → exposure_cap → crypto_exposure_cap
  → order_queue_missing → limit_price_missing → order_failed → …
```

Questo elenco è la mappa più onesta del comportamento del sistema: in esercizio reale ~99,9%
delle valutazioni termina in uno di questi rami, non in un ordine.

## 5. Ladder di uscita effettiva

Ordine reale in `_check_position_exit()` (chi scatta prima vince):

| # | Regola | Sorgente | Note |
|---|---|---|---|
| 0 | **min_hold 15 min** | `strategy.params.min_hold_minutes` | Sospende **tutto**, anche gli stop (riga 814) |
| 1 | ATR stop | `atr_daily × 2.5`, floor a hard_stop | per crypto quasi sempre = hard_stop (§9-D4) |
| 2 | hard stop | `risk.crypto.hard_stop_pct` = 6.0 | |
| 3 | trailing | `risk.crypto.trailing_stop_pct` = 4.5 su `peak_price` | |
| 4 | take profit | 5.0 | |
| 5 | partial TP | 1.0, ratio 0.5 | imposta `took_partial` in-place |
| — | *warmup grace 5 min* | | da qui in giù soppresso dopo cold start |
| 6 | peak detection | RSI>70 + close ≥ BB_upper(20) + OB imbalance < −0,2 (≥2 su 3) | usa BB **20**, non 50 |
| 7 | alpha decay | la strategia d'ingresso dice `sell`, dopo 30 min | |
| 8 | regime hold / time exit | `enabled: false` | |
| 9 | opportunity cost | `enabled: false` | |

Fuori da questa funzione, in `run_once`: circuit breaker per-simbolo (8% drawdown),
`stop_exit_reentry_cooldown` 30 min dopo uno stop, exit backoff 1/2/4/8/15 min.

**Asimmetria strutturale**: il take-profit parziale a +1% incassa metà posizione, il
`take_profit` pieno a +5%, mentre lo stop è a −6%. Con una distribuzione crypto reale il
rapporto vince/perde realizzato è ≈ 0.12–0.19 (§8, finding B-01). Questa è la ragione
meccanica del "84% win rate ma expectancy negativa".

## 6. Perché `min_conviction` non può vincolare

Con una sola strategia attiva:

```
conf_MR  ≥ confidence_floor = 0.4          (config: crypto_mean_reversion.confidence_floor)
buy_score = conf_MR × peso(1.0) ≥ 0.4
sell_score = 0  (non c'è nessuna strategia che possa vendere)  ⇒ lato singolo
soglia    = min_conviction × SSCM = 0.25 × 0.6 = 0.15
0.4 > 0.15  sempre                                        ⇒ nessun filtro di convinzione
```

Verificato anche con i correttivi: `_adjust_weights_for_regime()` modula solo strategie
spente; `ConfidenceCalibrator.calibrate()` non può abbassare la confidenza perché il suo
buffer è sempre vuoto (§8, B-02).

**Implicazione:** `min_conviction`, `single_sided_conviction_multiplier` e il meccanismo di
peso sono *decorazione* finché gira una sola strategia con un floor a 0.4. Sono anche dentro
il fingerprint dell'alpha gate, quindi cambiarli invalida una validazione senza cambiare
un singolo ordine.

## 7. Catena di sizing (il moltiplicatore composto)

```
max_pos_pct = 25%                                    (risk.crypto.max_position_size_pct)
            × vol_scale        [0.3 … 1.5]           (risk.vol_targeting, target 4% giornaliero)
            × portfolio_scale  [0.3 … 1.5]           (risk parity su covarianza 30 bar)
            × tod_scale        [0 … 1]               (_time_of_day_scale, no-op per crypto)
            × kelly_scale      [0.10 … 1.0]          ((2p−1)×0.5, p = win rate)
```

→ il "cap" del 25% non è un cap: il valore può arrivare a 25%×1.5×1.5×1.0 = **56%** in linea
teorica. Non ci arriva solo perché `kelly_scale` è quasi sempre al floor di 0.10 (p≈0.4–0.5 →
(2·0.45−1)·0.5 = −0.05 → clampato a 0.10). Il floor di Kelly è quindi l'unica cosa che
impedisce posizioni spropositate, ed è un limite accidentale, non progettato.

Ognuna è verificata sul codice. Le prime quattro sono quelle che rendono AGENTS.md
fuorviante su **come il sistema perde denaro**.

| ID | AGENTS.md dichiara | Il codice fa |

| **D5** | "`risk.crypto.max_daily_loss_pct: 5.0`" | Chiave mai letta; vale `risk.max_daily_loss_pct` = **3.0** |
| **D6** | "`is_market_open()` ritorna True 24/7 quando Crypto è in `trading_venues`" | Ritorna **False** sabato/domenica (verificato: 2026-11-14 15:00 UTC → False) e negli ultimi 30 s di ogni giorno UTC. | **D7** | "193 test, 16 skip" | 324 funzioni `test_` in 45 file. Conteggio non aggiornato |

## 10. Tre implementazioni della stessa strategia

Questo è il difetto architetturale che conta più di ogni singolo bug.

| Implementazione | Dove | Usa il codice di produzione? |
|---|---|---|
| Live | `app/strategies/crypto_mean_reversion.py` + `app/agents/trader.py` | — |
| Backtest agentico | `app/backtest/agent_engine.py` → `SimBroker` + **vero `TradingAgent`** | **Sì** (buono) |
| Validazione/gate | `scripts/alpha_validation.py` (`simulate()`, `prepare()`) | **No** — reimplementazione parallela |
| Backtest legacy | `app/backtest/engine.py` (SMA) | No, non correlato |

`alpha_gate` decide se il sistema può aprire posizioni leggendo un record prodotto
da `alpha_validation.py`. Migrare il gate sul motore agentico cambierebbe il verdetto, perché
le due implementazioni divergono su punti misurabili:

| Divergenza | Live | `alpha_validation.py` |
|---|---|---|
| hard stop | 6.0% | **5.0%** (default `ExitLadder.hard_stop`) |
| barra di riferimento del "drop" | `close[-drop_window-1]` (76 bar indietro) | `close.shift(75)` (75 bar indietro) |
| banda per peak detection | BB **20** (`indicators["bb_upper"]`) | BB **50** (`e.bb_period`) |
| trailing stop | su `peak_price` aggiornato dai tick | su chiusure di barra (più lasco ⇒ ottimista) |
| circuit breaker per-simbolo | 8% | assente |
| entry ranking, sentiment, vol targeting, exit backoff, min_notional | presenti | assenti |

Nessuna di queste è fatale, ma insieme rendono il "gate" una misura di *un modello della
strategia* e non della strategia. Il §"Alpha validation" di AGENTS.md lo presenta come
autorevole senza notare la differenza.
